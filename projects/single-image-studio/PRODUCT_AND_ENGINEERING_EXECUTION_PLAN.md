# 产品能力与工程演进执行计划

> 生效日期：2026-08-18
> 当前阶段：`Stage 1 · source/task controller extraction`
> 文档角色：本文件统一代码整理、可靠性、用户验证、现有能力质量和后续智能能力扩展的执行顺序。当前事实仍以 [STATUS.md](STATUS.md) 为准；长期能力证据与发布公式不由本文件改写。

## 1. 当前判断

Single Image Studio 已经拥有较宽的内部 Alpha 功能面，但还没有形成可邀请普通用户稳定使用的产品版本。

当前事实：

- 12 项本地任务在没有 API 时可运行；
- 透明抠图、商品图和报名照在背景移除 Provider 可用时开放；
- AI 老照片修复与创意改造仍是条件式实验能力；
- 产品测试、页面路由、错误、样例、走查和匿名汇总工具已经建立；
- 真人方法演练仍为 `0/2–3`，M2 为 `0/5–8`；
- `main.js` 仍承担过多页面和场景职责；
- 当前工作树尚未形成稳定 checkpoint。

因此后续不采用“只整理代码”或“只增加能力”的单线方案，而采用有依赖关系的双轨路线：

```text
工程轨：冻结基线 → 控制器拆分 → 持久化与可靠性 → 浏览器/治理
能力轨：质量矩阵 → 区域理解 → 自动构图 → 真正修复 → 生成式场景
```

能力轨必须建立在工程轨的稳定接口上，不得继续把场景逻辑直接堆入 `main.js`。

## 2. 当前能力分层

### 2.1 本地确定性底座

- 来源校验、EXIF 方向、裁剪、旋转、翻转；
- 拉直、垂直透视、四角裁正；
- 亮度、对比度、饱和度、轻度降噪与清晰度；
- PNG / JPEG、尺寸、压缩、画布适配与 metadata 清理；
- 文档归档、上传规格、隐私分享；
- 社交模板、标题、九宫格、老照片基础整理；
- 多规格结果、ZIP、重开、像素、Hash 与下载资格检查。

### 2.2 条件式背景移除能力

- 透明抠图；
- 蒙版擦除 / 保留修正；
- 透明 PNG 与纯色 JPEG；
- 商品图和报名照构图与套装。

纯色换底是抠图结果的派生交付动作，不再作为独立顶层任务重复登记。

### 2.3 实验性生成能力

- AI 老照片修复；
- AI 创意改造。

这些入口只证明接口与风险边界，不证明模型质量、身份保真、文字保真或可发布性。

### 2.4 尚缺的智能能力

- 主体、人脸、商品和文档区域理解；
- 自动构图与裁剪建议；
- 文档自动找边、阴影 / 反光 / 曲面处理；
- 真正的划痕修复、去模糊、超分与上色；
- 背景生成、扩图、重新照明和指定区域重绘。

## 3. 遗留工作优先级

### P0 · 必须先收口

1. 审计并提交当前工作树，形成可回滚 checkpoint；
2. 清除顶层任务目录中已经作为派生动作实现的重复身份；
3. 拆分 `main.js` 高风险职责；
4. 保持来源、结果、下载和远程幂等安全边界。

### P1 · 邀请测试前必须完成

1. 2–3 人方法演练及必要界面修正；
2. 16–24 张代表性图片质量矩阵；
3. PhotoRoom 或替代 Provider 的质量、成本、保留与删除核对；
4. 真实 Chrome / Edge 指针、键盘和下载检查；
5. 明确远程任务跨服务重启的恢复策略。

### P2 · 现有能力优化

1. 文档、压缩、增强、老照片和抠图的自然图片分层质量；
2. 商品、报名照和社交构图的用户理解与人工调整负担；
3. 可访问性、布局密度和错误恢复一致性。

### P3 · 新能力

1. 图片区域理解；
2. 自动构图；
3. 真正照片修复；
4. 生成式背景、扩图和重新照明；
5. 有证据支持后再考虑批量、移动端、本地模型和官方规格。

## 4. 分阶段执行

### Stage 0 · 整理并冻结当前成果

动作：

1. 审计全部 modified / untracked 文件；
2. 检查密钥、缓存、依赖目录和临时结果；
3. 清理 `UT-SOLID-BG` 顶层任务语义；
4. 运行产品测试、语法、页面注册、13 路由和 `git diff --check`；
5. 提交 `internal-alpha checkpoint`。

退出条件：

- 工作树干净；
- checkpoint 可回滚；
- 现有功能、页面和证据可由固定提交重现。

### Stage 1 · 代码结构收敛

按以下顺序做无行为变化抽离：

1. `source-task-controller`：来源、确认、换图、任务导航；
2. `settings-controller`：设置装配、字段错误和配置状态；
3. `local-execution-controller`：本地渲染与套装；
4. `remote-execution-controller`：Provider、轮询、取消与 UNKNOWN；
5. `result-workbench-controller`：比较、修边、背景与下载；
6. `scenario-adapters`：商品、报名照、社交和老照片专属 UI。

每次只抽一个责任，不同时改变视觉、文案和任务合同。

退出条件：

- `main.js` 只负责装配与顶层状态迁移；
- 场景不再向主控制器添加大段分支；
- 每个状态有单一所有者；
- 产品与浏览器基线无回归。

### Stage 2 · 固定 build 的真人走查

1. 使用项目合成图进行 2–3 人方法演练；
2. 固定 build、浏览器、视口和任务原文；
3. 导出匿名 JSON 并本地汇总；
4. 只修复真实观察到的 P0 / P1 / P2；
5. 决定是否进入 5–8 人 M2。

### Stage 3 · 代表性图片质量矩阵

准备 16–24 张项目原创或明确许可图片：

- 基础编辑：横、竖、长、透明、大图、文字图；
- 文档：倾斜、透视、阴影、低对比、复杂背景；
- 抠图：头发、毛发、玻璃、镂空、低对比；
- 老照片：人脸、文字、划痕、模糊和褪色。

每张记录适用任务、自动结果、人工修正负担、失败类型和可用性，不允许只保留成功案例。

### Stage 4 · 图片区域理解 v1

第一版只输出建议，不自动修改：

- 文档四角；
- 人物 / 主体范围；
- 重要内容安全区；
- 推荐构图与无法判断状态。

首批消费者：文档裁正、报名照、商品图、社交裁剪。

### Stage 5 · 真正照片修复 Provider v1

1. 建立供应商无关 `RestorationProvider`；
2. 选择可直接接收图片且治理边界可接受的实现；
3. 冻结有限修复选项；
4. 保留原图，结果只作为副本；
5. 检查人物、文字和历史细节变化；
6. 增加局部对比、成本、保留与删除说明。

### Stage 6 · 生成式场景

按价值顺序评估：背景生成 → 扩图 → 重新照明 → 指定物体 / 文字移除 → 宣传图布局。

### Stage 7 · 邀请测试准备

- 持久任务记录或明确的不可恢复边界；
- 真实 Chrome / Edge 输入与下载；
- Provider 限流、成本、恢复、保留和删除；
- 5–8 人内部走查；
- 输出 `prepare / iterate / stop / narrow` 决策之一。

## 5. 新能力固定交付清单

以后每项新能力必须在同一工作包中关联：

1. `task-catalog` 身份与可用性；
2. `WorkflowDefinition` / Provider / renderer 合同；
3. 产品入口和不可用原因；
4. 设置、执行、结果和错误恢复；
5. 项目原创样例或明确的参考边界；
6. 自动测试与真实浏览器路径；
7. 页面注册与父入口；
8. README、STATUS、任务与能力文档；
9. 数据、权限、成本与非能力声明。

缺少任一项时只能是实验，不得标记为产品能力完成。
