# Single Image Studio 产品稳定化执行路线

> 生效日期：2026-08-17
>
> 适用阶段：内部 Alpha
>
> 文档角色：本文件是未来 3–5 周的短周期执行总纲。当前事实以 [STATUS.md](STATUS.md) 为准；长期产品与研究边界继续由 [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)、[ROADMAP.md](ROADMAP.md) 和证据文档保存。

## 1. 当前判断

项目已经越过“只能演示一个按钮”的阶段，但还没有达到可公开发布的完整产品阶段。

当前已经成立的是：

- 单图上传、来源绑定、裁剪 / 旋转 / 调整、压缩、格式转换、画布适配和可靠下载等本地基础能力可以组合使用；
- 文档裁正、文档归档、上传规格适配、老照片基础整理、社交模板、商品图和报名照等场景已经有内部试用路径；
- PhotoRoom 抠图作为可选远程能力已经接入，并配有本地蒙版修正、换底和导出；
- Codex 内置 Chromium 的五条本地真实页面流程已经 `5/5 pass`；现有产品验证命令保持全绿；
- 这些事实构成“内部 Alpha 工程基线”，不等于真实图片质量、多人可用性、公开发布或全部场景均已完成。

当前主要风险已经从“有没有功能”转为：

1. 页面主控制代码承担过多职责，继续堆功能会增加回归和状态分叉；
2. 已有能力很多，但用户不容易知道处理前后差异、适用场景和能力边界；
3. 错误信息仍分散在不同路径，用户不总能判断是否上传、是否可重试、结果是否安全；
4. 场景功能容易退化成一组孤立按钮，缺少统一、可复用的工作流结构；
5. 外部 Provider、Codex 测试能力与软件本地能力容易被混为一谈。

因此，下一阶段不再以功能数量为目标，而以“稳定、可理解、可组合、可验证”为目标。

## 2. 产品目标与非目标

### 2.1 本阶段目标

让普通用户完成以下闭环，而不需要理解模型、格式协议或内部任务编号：

```text
选择图片
→ 选择想解决的问题
→ 看懂将发生什么
→ 调整必要参数
→ 看到完整且可信的结果
→ 明确知道成功或失败
→ 下载，或把结果继续用于下一步
```

本阶段完成时应具备：

- 一个职责清晰、可以继续扩展的前端结构；
- 一个能展示真实样例、处理步骤和限制的效果页；
- 一套覆盖本地与远程任务的统一错误呈现；
- 一个统一的场景工作流定义方式，而不是继续在主文件中硬编码分支；
- 一组固定浏览器回归和少量内部用户走查结果；
- 对是否进入邀请测试的明确 `go / iterate / stop` 决策。

### 2.2 本阶段非目标

- 不追求一次完成所有图片场景；
- 不下载或部署 MODNet、RVM、SAM 等本地模型；
- 不创建新的 normalize / export 研究 Slice；
- 不把 Codex 生成的展示图冒充产品运行时输出；
- 不把 PhotoRoom、MiniMax 或其他服务写成产品必需依赖；
- 不接收、保存或用于训练真实参与者照片；
- 不宣称官方证件照规格、平台审核通过、AI 老照片真实性或公开发布就绪。

## 3. 设计原则

### 3.1 本地底座优先

裁剪、方向、压缩、格式、画布、文档校正和本地增强必须在没有 API 时仍然可用。远程服务失败时，用户仍能回到这些能力，而不是整个产品失效。

### 3.2 场景是能力组合，不是复制功能

“报名照”“商品图”“文档附件”应由同一批底层能力按固定步骤、默认值和验收规则组合。场景层只增加用途、顺序、默认参数和检查，不复制渲染或下载实现。

### 3.3 Provider 可替换

抠图或生成式处理通过 Provider 接口接入。界面只理解“需要远程处理、需要逐次同意、可能失败”，不依赖供应商字段。未配置 Provider 时，本地能力和不依赖模型的场景必须正常工作。

### 3.4 证据与展示分离

展示页中的每张图必须标记来源：项目原创、Codex 生成参考、PhotoRoom 沙盒结果或其他明确许可来源。静态演示不能冒充本次浏览器实际处理结果。

### 3.5 先形成退出条件，再开始开发

每个阶段先写清楚“怎样算完成”。未达到退出条件时不同时开启更多场景；达到后立即进入下一阶段，不继续无限微调同一个控件。

## 4. 执行阶段

时间是顺序估算，不是发布承诺。发现影响来源安全、下载正确性或远程重复计费的问题时，立即停止后续阶段并先修复。

### S0 · 固定当前内部 Alpha 基线（已完成，持续守护）

目标：把已经验证的能力变成后续重构不可破坏的回归线。

已有基线：

- `verify:product` 全绿；
- 浏览器五条流程 `5/5 pass`：基础编辑、社交构图、老照片整理、上传规格适配、文档归档；
- PNG / JPEG 结果完成签名、尺寸、重开、完整显示、旧下载失效和焦点检查；
- PhotoRoom 远程抠图可以运行，但仍是可选、沙盒和质量未正式证明的 Provider。

守护规则：

- 后续每次结构调整都必须保持产品测试全绿；
- 修改导航、设置、结果或错误页时，至少重跑对应浏览器流程；
- 任何失败都必须说明是产品缺陷、测试缺陷还是环境缺陷，不能通过放宽断言“修好”。

### S1 · 代码质量与结构收敛（Now，预计 3–5 个工作日）

目标：在不改变用户行为的前提下，降低继续扩展时的回归风险。

执行动作：

1. 列出 `web/main.js` 当前职责、状态所有者、事件入口和跨模块依赖；
2. 优先抽离纯逻辑和显示模型，不先重写渲染器：
   - 来源与任务导航；
   - 场景工作流装配；
   - 结果页 view model；
   - 错误分类与恢复动作；
   - 本地 / 远程执行边界；
3. 建立统一 `WorkflowDefinition` 合同，至少包含：
   - `id`、用途与适用输入；
   - prerequisite 与可用性原因；
   - 参数和默认值；
   - 有序步骤；
   - 输出集合；
   - 结果检查；
   - 错误边界与恢复动作；
4. 把重复 DOM 查询、状态切换和结果标签集中到单一入口；
5. 为抽出的每个模块补纯函数或 DOM 合同测试；
6. 删除确认不可达的分支，但不在同一提交中改变交互或视觉。

交付物：

- 一份主流程依赖图和职责清单；
- 至少完成第一批高风险职责抽离；
- 统一工作流定义的代码合同和测试；
- 重构前后行为对照记录。

退出条件：

- 产品测试和五条浏览器基线无回归；
- 一个场景可以仅通过新增 / 组合工作流定义接入，不必修改多个页面状态分支；
- 远程失败不会污染本地结果，旧任务不会解锁新下载；
- 代码评审能清楚回答“来源、设置、执行、结果、错误分别由谁负责”。

### S2 · 样例与效果展示页（Next，预计 2–4 个工作日）

目标：让用户先看懂产品能做什么、适合什么图片、结果会有什么变化。

执行动作：

1. 新建 `/examples.html`，作为产品展示与内部质量复核页，而不是新的处理入口；
2. 建立 `examples-manifest`，每个样例记录：
   - 来源和许可；
   - 原图与结果文件身份；
   - 使用场景、步骤和关键参数；
   - 本地或远程处理；
   - 输出尺寸、格式与体积；
   - 能力边界和已知问题；
3. 第一批至少覆盖六类：
   - 基础裁剪 / 旋转；
   - 文档裁正 / 归档；
   - 压缩 / 格式 / 画布适配；
   - 老照片本地基础整理；
   - 社交模板或九宫格；
   - 透明抠图与换底；
4. 提供完整原图、结果图、并排 / 滑动对比和参数摘要；
5. 从样例页可进入对应场景，但不会自动上传、执行或产生付费调用。

退出条件：

- 所有展示资产有来源标签和文件清单；
- 原图与结果都完整显示，不因容器比例被截断；
- 用户能在 30 秒内回答“这个场景解决什么、是否需要联网、结果能下载什么”；
- 静态参考、Codex 生成图和真实运行结果在视觉与文字上明确区分；
- 不存在只有标题、没有真实对照的空场景卡。

### S3 · 统一错误与恢复体验（Next，预计 2–4 个工作日）

目标：错误发生时，用户知道发生了什么、图片是否发送、是否安全重试，以及下一步能做什么。

统一错误分类：

| 类别 | 必须告诉用户的内容 | 默认主动作 |
| --- | --- | --- |
| 输入不支持 | 文件或尺寸哪里不符合要求 | 重新选择图片 |
| 设置不合法 | 哪个字段有问题、允许范围是什么 | 聚焦并修改字段 |
| 本地处理失败 | 原图仍在本机、未上传 | 调整设置或换本地任务 |
| 输出校验失败 | 文件未进入下载资格 | 返回设置 |
| 远程明确失败 | 是否已发送、是否可能计费、结果未采用 | 改用本地或重新确认后重试 |
| 远程状态未知 | 不能确认终态、禁止自动重复提交 | 查询原任务 |
| 网络 / 服务不可用 | 哪项能力受影响、本地能力仍可用 | 使用本地工具 |

执行动作：

1. 建立统一 `ErrorPresentation` 映射，不让页面直接拼接供应商错误；
2. 错误卡固定显示：普通语言标题、发生了什么、数据边界、恢复动作、任务编号；
3. 技术错误码、HTTP 状态和诊断详情默认折叠；
4. 表单错误必须在设置页原位展示并聚焦，不能让点击“生成”后无反应；
5. 为超时、取消、UNKNOWN、失效来源、旧下载、输出重开失败和 Provider 禁用建立固定页面夹具；
6. 错误页也要保持当前原图完整可见，除非来源本身已失效。

退出条件：

- 每个错误分类都有确定的页面状态、主动作和自动测试；
- 不再出现“停在设置页但没有说明”或“结果页和错误页都没出现”；
- UNKNOWN 不自动重试，明确失败不阻止本地继续；
- 普通用户无需理解 Provider、run state 或协议术语即可选择下一步。

### S4 · 场景工作流扩展（Later，单场景 3–5 个工作日）

目标：用统一工作流组合现有能力，每轮只增加一个有明确用户问题的场景。

场景进入开发前必须回答：

1. 用户在什么情况下遇到这个问题？
2. 输入图片有什么限制？
3. 哪些步骤可以完全本地完成？
4. 哪一步真的需要模型或 Provider？
5. 没有 Provider 时是否仍有有用结果？
6. 最终交付是一张图、一组图还是一个压缩包？
7. 如何独立验证尺寸、格式、体积和视觉完整性？

优先候选：

1. **隐私分享副本**：自动移除可识别 metadata、限制尺寸 / 体积、可选局部遮挡；本地优先；
2. **平台发布套装**：从一张结果派生多个明确像素规格和体积上限；不冒充平台审核；
3. **透明素材交付包**：透明 PNG、白 / 黑底检查图和尺寸清单；抠图 Provider 可选；
4. **文档提交包**：裁正、清晰彩色 / 灰度、附件压缩、文件命名和一组交付；本地完成；
5. **创意宣传图**：本地布局先行，生成式背景或素材作为可选 Provider；未配置时仍能使用模板和本地图层。

Skill 与运行时的边界：

- Codex / image generation skill 用来生成项目原创测试素材、视觉参考和展示候选，不是网页运行时服务；
- PhotoRoom 是当前可选抠图 Provider；
- MiniMax 或 OpenAI 图片模型只有在明确接口、隐私、成本和授权后才可作为生成式 Provider；
- 场景工作流必须首先组合软件已有独立能力，不能因为没有模型就整张卡不可用，除非该场景本质就是生成式编辑。

退出条件：

- 新场景通过统一 `WorkflowDefinition` 接入；
- 至少有一组项目原创端到端样例；
- 有明确输入限制、步骤、输出和失败恢复；
- 本地和远程步骤可被用户区分；
- 未增加绕过来源绑定、结果校验或下载门控的第二条实现。

### S5 · 真实页面回归与内部走查（预计 3–5 个工作日）

目标：验证用户是否真的能完成任务，而不是只证明测试脚本能点击按钮。

执行动作：

1. 固定桌面最小和常规视口，重跑基础五流程及新增样例 / 错误路径；
2. 使用项目原创或明确许可图片，不接收参与者个人照片；
3. 先进行 2–3 人走查修正明显理解问题，再完成计划中的 5–8 人内部走查；
4. 分开记录：任务完成率、首次找到入口、参数理解、错误恢复、下载成功和主观信心；
5. 对抠图另做专项走查，不把本地编辑成功率替代抠图质量。

当前进度（2026-08-18）：内部质量入口、走查台、两项固定任务、strict 匿名 JSON、本地去标识汇总和 13 项页面—能力注册表已完成；以后新增页面必须同时登记角色、父入口和真实 task 关联。1180 / 390 px 浏览器工具 QA 为 `2/2`，但真人方法演练为 `0/2–3`、M2 为 `0/5–8`。下一动作不是继续加场景，而是实际邀请 2–3 位未参与设计的人，仅使用项目合成图完成走查并汇总入口、理解、下载和边界问题。

退出条件：

- 关键任务无阻断级缺陷；
- 形成性任务达到预先登记的 80% 完成门槛，或明确记录未通过原因；
- 错误恢复不导致重复远程提交或旧结果下载；
- 所有未解决问题都有严重级别、负责人、复现步骤和去向。

### S6 · 邀请测试准备决策（1–2 个工作日）

本阶段只作决策，不等于上线。只能输出以下之一：

- `prepare-invite-beta`：准备窄范围邀请测试；
- `keep-internal-and-iterate`：继续内部 Alpha；
- `stop-remote-provider`：停用当前远程 Provider，保留本地产品；
- `start-local-model-study`：产品数据证明离线 / 隐私 / 成本需求后，单独立项本地模型；
- `narrow-product-scope`：删除低价值场景，集中高完成率路径。

公开发布仍需另行满足 C / U / E / R / O / G / V 和 Release Gate；本计划不会把内部浏览器通过自动升级为发布证据。

## 5. Now / Next / Later

### Now

1. 固定本文为当前短周期执行入口；
2. 完成 `main.js` 职责清单、状态所有权和依赖图；
3. 选择第一批无行为变化的抽离边界；
4. 把现有产品测试与浏览器 `5/5` 设为重构回归门；
5. 建立样例资产清单，禁止来源不明图片进入展示页。

### Next

1. 完成第一轮结构拆分；
2. 落地 `/examples.html` 与至少六类对照样例；
3. 落地统一错误分类、错误卡和恢复动作；
4. 为设置无响应、远程 UNKNOWN 和输出校验失败补真实页面验收。

### Later

1. 按统一工作流框架选择并实现一个新场景；
2. 完成 2–3 人预走查与 5–8 人内部走查；
3. 形成邀请测试 go / no-go 决策；
4. 只有产品数据证明必要时，恢复本地模型或新增生成式 Provider 研究。

## 6. 工作项优先级

统一采用以下顺序：

```text
P0 数据安全、错误下载、重复付费、来源错绑、结果错绑
P1 任务无法完成、无错误说明、结果截断、状态不可恢复
P2 理解成本高、布局和键盘体验差、缺少对照与说明
P3 新场景、视觉装饰、非关键参数和实验性 Provider
```

同一周期若出现 P0 / P1，暂停新增场景。P2 可以与样例页和错误体验一起处理。P3 只有在当前阶段退出条件满足后进入。

## 7. 每次继续开发的固定动作

后续每次开始工作时按以下顺序执行：

1. 读取 [STATUS.md](STATUS.md) 和本文，确认当前阶段；
2. 查看工作树，区分已有用户改动和本次范围；
3. 写出本次唯一主要结果及不做事项；
4. 先补失败复现或测试，再修改实现；
5. 运行定向测试；
6. 运行 `npm run verify:product`；
7. 涉及页面时启动服务并在浏览器检查目标状态、错误状态和两档视口；
8. 运行 `git diff --check`，核对没有密钥、依赖目录或临时结果；
9. 更新 STATUS / 证据文档，只记录实际发生的事实；
10. 达到当前阶段退出条件后，才把下一阶段设为 Now。

## 8. 完成定义

“开发完成”至少同时满足：

- 功能从真实入口可到达；
- 成功、拒绝、失败和未知状态都有界面；
- 原图与结果完整显示；
- 输出经过格式、尺寸、体积、像素或哈希中适用项的独立检查；
- 旧来源、旧任务和旧下载不会覆盖当前状态；
- 本地 / 远程、是否上传、是否可能计费表达清楚；
- 有定向测试和浏览器证据；
- 文档只声明实际能力和限制；
