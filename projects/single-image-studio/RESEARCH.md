# 研究计划

> **归档重基线（2026-08-16）**：本文件保存长期能力研究、证据等级和公开发布路线，不再规定近期产品实现顺序。当前执行以 [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) 为准：先完成无模型基础编辑器和早期内部可用性走查，再评估可替换云端抠图 Provider；不创建 Slice 12，也不把 MODNet / RVM 本地运行时作为 MVP 前置条件。下文的 C/U/E/R/O/G/V 与 V1 门继续约束冻结研究、公开声明和发布，不阻止构建内部产品试用版。

下文保留的“本轮目标”“研究顺序”“最后才”等措辞均属于 **2026-08-16 以前冻结的历史研究路线**，只能用于解释证据 lineage，不得被执行者当作当前施工顺序。

## 当前结论

当前仓库中的可运行页面、服务端代理和自动检查只构成 **R0 工程探针**：它证明部分状态、请求和下载边界可以被实现，但不证明任何原子能力、用户可见效果、生产闭环或用户价值已经成立。现有演示图、概念图和历史 Skill 结果也不能替代当前引擎、当前输入契约和冻结夹具上的复验。

本轮目标不是继续堆页面，而是建立一套可复用、可替换、可测量的单图能力体系，并用真实结果决定第一版产品包含什么。研究顺序为：

1. 先打透主体 / 背景底座。
2. 再验证保真、自然的图片增强。
3. 用同一套证据设施对测 CR1 与 CR2 两个创意方向。
4. 补齐管线闭环、运维和治理证据。
5. 用 6–8 名目标用户做形成性测试并冻结验证契约。
6. 最后才开发最小冻结桌面验证界面，完成至少 18 名新用户的 `V1-validation`；通过设计入场门后才重设计正式桌面浏览器产品页面。
7. 正式页面必须重新取得 `R1-product-release`，并按等价变更规则迁移或重做受影响 V1，之后才开放混合邀请 beta。

旧的全局 Stage 门槛不再使用。每项能力沿自己的证据轴推进；创意方向没有达到 E1 时混合产品门不通过，但不阻塞主体 / 背景、自然增强、运行设施、治理或形成性研究。

首轮 V1 与发布声明只覆盖冻结的 Windows 桌面 Chromium 环境：Chrome / Edge 精确稳定版本、`1280 × 720` 与 `1440 × 900` 视口、键盘 / 鼠标 / 缩放范围写入 CompatibilityProfile。手机、平板、Safari、Firefox、iPhone / HEIC 与完整响应式产品均不进入首轮分母。

## 研究成功问题

最终只回答一个产品问题：

> 目标用户能否在三分钟内、最多执行两次，得到一个通过任务 QA、自己认为可用并主动下载的真实结果？

在冻结用户验证前，任何内部判断、工程演示、浏览器测试或好看的单次结果都不能回答这个问题。

## 九类原子能力

本文件只使用 [CAPABILITY_MAP.md](CAPABILITY_MAP.md) 冻结的权威分类。九类能力是研究目录，不是首版功能清单；用户效果和场景必须引用这些能力合同，不能另建一套平行编号。

| ID | 能力域 | 当前研究职责 |
| --- | --- | --- |
| `CAP-01` | 来源资产 | 文件真实性、来源 hash、处理授权、隐私和版本关系，产出 `ImageAsset` |
| `CAP-02` | 归一交付 | 方向、颜色空间、尺寸、编码、透明度、元数据清理和正式下载产物 |
| `CAP-03` | 图片理解 | 形成可审计 `SourceCard`；只记录主体、质量、文字和背景等客观信号 |
| `CAP-04` | 主体区域 | 检测、分割、Alpha Matting、区域选择与必要的人工修正 |
| `CAP-05` | 几何合成 | 在不重画受保护内容的前提下裁切、缩放、定位和确定性合成 |
| `CAP-06` | 质量修复 | 自然光色 / 清晰度、no-op、降噪、去模糊和后续重建型修复的分界 |
| `CAP-07` | 生成编辑 | 局部修补、扩图、背景生成和 CR1 / CR2 参考驱动创意重构 |
| `CAP-08` | QA 证据 | 任务 QA、运行与证据 manifest、失败拒绝、下载和发布门禁 |
| `CAP-09` | 编排推荐 | 硬资格、能力 DAG、可解释排序、成本 / 耗时选择、重试和失效传播 |

当前纵切依赖为：`CAP-01 + CAP-02 + CAP-03` 提供来源与规范输入；先验证 `CAP-04 + CAP-05 + CAP-08` 的主体 / 背景；再验证 `CAP-06 + CAP-08` 的自然增强和 `CAP-07 + CAP-08` 的 CR1 / CR2。`CAP-09.execute` 作为早期确定性控制面运行这些数据 DAG；`CAP-09.recommend` 最后只在已经取得效果证据的版本之间做资格、排序与解释，不进入 U1 / E1 的像素质量依赖。

商品图、头像、社交图片和纪念图片是能力组合，不是重新开发的原子能力。批量、团队、API 和场景配方只有在单图能力成立后再决定。

## 四套互斥集合与 fixture suite

权威的四套互斥集合是：

| 集合 | 用途 | 隔离要求 |
| --- | --- | --- |
| `dev/calibration` | 候选筛选、阈值校准、失败分类和配方调整 | 可以查看和调参，但不能作为独立验收成绩 |
| `holdout` | 冻结合同、版本、分母、阈值和停止规则后的正式验收 | 预注册前不得查看或用于演示；运行后不得继续调参并沿用同一证据 |
| `defect` | 注入可定位灾难缺陷，证明 `CAP-08` 能拒绝坏结果并量化误拒绝 | 不替代自然输入质量评测 |
| `escape` | 保存真实运行中被现有 QA 漏过的最小复现，供下一版本回归 | 不回写历史 holdout，也不默认吸收生产用户图 |

`NORMALIZE-DELIVER`、`MATTE-GT`、`MATTE-REAL`、`NATURAL-DEGRADE` 和 `CREATIVE-COVERAGE` 只是**题材 / 任务 fixture suite**，不是另外五套集合；suite 目录可随能力研究扩展：

- `NORMALIZE-DELIVER`：方向、ICC / sRGB / CMYK、位深 / HDR、预乘 Alpha、动画策略、格式损坏、尺寸 / 体积边界与正式交付重开验证。
- `MATTE-GT`：具有可追踪 Alpha 真值的分层或受控合成题材，覆盖人物、硬边物件、发丝 / 毛发、孔洞、细结构和半透明；保存前景、Alpha、背景、合成过程和 hash。
- `MATTE-REAL`：权利清楚的真实困难边缘题材，覆盖卷发、眼镜、帽饰、白物白底、低对比、反光、阴影、运动模糊、细杆和复杂背景；用于真实视觉边缘与拒绝边界。
- `NATURAL-DEGRADE`：权利清楚的清洁原图及版本化脚本产生的曝光、白平衡、低对比、噪声、轻度模糊和压缩退化对；原图是保真参考，生成模型不得制造真值。
- `CREATIVE-COVERAGE`：近景人物、动作人物、单物 / 商品、动物、建筑 / 室内、风景和密集现场等题材；保存 must-keep、允许改变、主体数量、关键物件、文字和参考敏感点。

每个 suite 都要把不同来源资产分配到 `dev/calibration` 与独立 `holdout`；相应坏结果进入 `defect`，真实漏检最小复现进入 `escape`。四个集合之间不得复用图片、近重复图片、同一拍摄序列或同源衍生版本。每项资产只能属于一个集合，并在 manifest 中记录 suite、集合、来源族、拍摄 session、派生链、感知去重、许可、人物 / 品牌状态、EXIF 清理和 SHA-256。真实用户上传永远不自动进入任何研究集合或样例目录，也不因失败、DETACHED 或 escape 需要而默认长期留存。

## 首轮研究顺序

### 1. 主体 / 背景底座

先用同一适配接口比较至少两个在共同适用分母上真正输出连续 Alpha 且许可允许研究的候选、一个已登记基线和可用市场基准；粗分割不冒充 Matting，市场基准不可取得时预注册缺席。固定 `normalize → detect / segment → matte → edge-refine / decontaminate → 黑白彩底预检 → 可选 correction revision → render → export → 重开与最终 QA`，并分别报告自动首轮与修正后结果。原子分割 / Matting 达到 C1 后，才组合成透明主体和纯色换底两个实用效果并争取 U1。

纯色换底必须复用已记录的 Alpha，并通过确定性合成锁住安全前景像素。不得用生成式换背景掩盖蒙版缺陷，也不得把“抠图、去背景、透明底”计成三个原子能力。

### 2. 自然增强

在 `NATURAL-DEGRADE` suite 的 `dev/calibration` 上建立简单、可解释的确定性基线，再冻结版本并在独立 `holdout` 上验证保真增强。允许改变曝光、白平衡、对比、噪声和适量锐度；不允许重画脸、增加不存在的纹理、删除对象、自动换背景或静默裁切。

自然增强按自己的 C1 / U1 证据推进，不依赖创意效果是否成功。

### 3. CR1 / CR2 创意对测

只对测两个高差异方向：

- CR1：手绘记忆重构。
- CR2：结构套色重组。

两者使用与未来运行一致的来源 / 参考输入契约。首轮比较来源可辨认、人物或物件数量、must-keep、视觉变化、效果身份、假文字 / 水印、参考泄漏、延迟和成本；进入复验后再检查同一冻结版本的重复性。

CR1 / CR2 均未达到 E1 时，结论是“混合产品门不通过”，不是暂停主体 / 背景、自然增强或产品基础研究。

## 证据轴

各证据轴回答不同问题，不能相互替代：

| 证据 | 含义 | 取得条件 |
| --- | --- | --- |
| C1 | 原子能力成立 | 单一、版本化能力在预声明分母和独立 `holdout` 上可重复运行，满足冻结能力指标、拒绝、重复性与失败边界，并保留完整记录 |
| U1 | 实用效果成立 | 一个用户可理解的实用结果由已验证原子能力组成，在生产等价任务契约下通过冻结质量、任务 QA、适用 / 拒绝和重复性门槛 |
| E1 | 创意效果成立 | 冻结配方与输入契约跨预声明适用类别保持来源关系、效果身份和最低成功率，并记录全部失败与重复性 |
| R1-pipeline | 无界面管线闭环成立 | 上传 / 读取 → 分析 → 执行 → QA → 比较资产 → 下载资产的生产等价链可重复运行，成功、拒绝、错误、超时和过期响应均有证据 |
| R1-product | 产品闭环成立 | 绑定精确 surface / build 的界面使用同一任务契约和后端，按版本化 acceptance matrix 跑通真实交互、恢复、比较与下载；验证壳记为 `R1-product-validation`，正式页面另取 `R1-product-release` |
| O1 | Operational 运维成立 | 版本化 O1Profile 已冻结工作负载、环境、分层分母、并发、时延 / 成本、错误预算与恢复目标，且幂等、有限重试、UNKNOWN、日志、删除、备份和故障演练达标 |
| G1 | Governance 治理成立 | 来源与许可、用户处理权和数据告知、模型 / 服务条款、版本与发布 allowlist、安全策略、密钥与审计边界完整 |
| V1 | 用户价值成立 | 形成性修改结束并冻结产品后，由至少 18 名新的目标用户完成预注册验证；达到冻结成功门槛，而不是只报告主观好评 |

当前状态统一记为 **R0 工程探针**。在相应记录真正完成前，不提前声明 C1、U1、E1、R1-pipeline、R1-product、O1、G1 或 V1。

## 用户研究与冻结

### 形成性测试

- 使用 6–8 名目标用户。
- 招募、同意、参与者图片权利、敏感内容、退出与删除依照 [USER_RESEARCH_PROTOCOL.md](USER_RESEARCH_PROTOCOL.md)。
- 可以由研究人员协助，也可以使用低保真壳层，但所有结果必须来自真实任务管线。
- 观察用户是否理解任务卡、保留 / 改变边界、等待状态、失败原因、比较与下载。
- 这一轮允许修改文案、排序、规则、样例、任务设置和恢复流程，因此不能计入 V1。
- 形成性研究可以按已达标的实用或创意任务分别开展，不等于已经开放“质量 + 主体 / 背景 + 创意”的混合邀请测试。

### 冻结验证

形成性问题修正后，冻结：任务目录、资格规则、参考对、任务契约、管线 / 配方版本、QA、核心文案、验证交互和成功定义。随后只开发支撑真实任务研究所需的**最小冻结桌面验证界面**并取得 `R1-product-validation`；它不是正式桌面产品页面，也不承担移动验证。再邀请至少 18 名未参加形成性测试的目标用户，对同一冻结 Windows / Chromium 任务与环境范围进行 `V1-validation`。总人数不能代替分项覆盖，必须用 `V1Scope` 冻结每个 effect / variant 的最小有效人数、ITT / eligible 分母、拒绝 / 退出处理、主估计量和置信区间。

每名用户的核心任务只有一个成功定义：

> 从选择图片开始，在三分钟内、最多两次真实执行中，得到一个通过任务 QA、本人认为可用并主动下载的结果。

正式开始前预注册 V1 的总体与分项门槛、分组观察项、主持人介入上限和无效会话规则；验证过程中不得为提高结果而修改冻结版本。发生实质修改时建立新版本和新一轮验证，不能把前后数据合并。下载只是联合成功条件之一，不能单独作为需求成立的代理。

### 正式页面设计入场与混合邀请 beta

以下三项必须同时满足，才可开始正式桌面浏览器产品页面重设计：

1. `effect.natural-enhance` 取得 U1。
2. `effect.subject-background` 至少一个透明或纯色 variant 取得 U1。
3. CR1 / CR2 至少一个取得 E1。

这里“满足”指各自依赖能力 C1、R1-pipeline、`R1-product-validation`、O1、G1、相应 `V1-validation` 和验证界面用户可见资产 Release Gate 均完整，不是只取得一张好图。创意 E1 未成立时，底座、C1 / U1、R1-pipeline、O1 / G1 和形成性研究继续；但不得继续做混合产品 UI。若要改成纯实用产品，必须另行获得用户批准并重新冻结产品范围。

正式桌面页面改变了 surface 版本，旧产品与用户证据不得自动继承。完成后必须在冻结 Windows / Chromium 范围取得 `R1-product-release`；只有预注册等价变更清单内、不改变任务发现、信息层级、控件、状态、文案、桌面视口行为、数据告知或下载行为的变化，才可用桥接测试迁移 V1。其他变化要为受影响 scope 重新取得 `V1-release`。所有 release surface 证据和资产门槛满足后，才可开放桌面混合邀请 beta。

## 明确后置

- 多图逐张、批量和目录处理。
- 用户挑选多个满意结果后的合集、故事、轮播或网页。
- 海报、封面、卡片、故事册和完整设计画布。
- 特定护照、签证、身份证、考试或机构官方证件照。
- 自由 Prompt、模型市场、Skill 选择器、视频 / 音频、模板素材库和团队后台。
- 手机、平板、Safari、Firefox、iPhone / HEIC、触摸专属交互与完整响应式产品。

通用底色头像也只有在 `CAP-04 + CAP-05` 底座、身份保护与独立夹具成熟后才研究；它不自动继承主体 / 背景效果的 U1，更不得声称官方受理。
