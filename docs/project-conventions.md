# 子项目约定

## 1. 目录与命名

- 本仓库内的研究项目放在 `projects/<project-slug>/`。
- `project-slug` 使用小写 `kebab-case`，尽量与上游仓库或独立仓库名称对应。
- 不在子项目中保留嵌套 `.git`。需要独立历史时，使用明确的多仓库方案。
- 只创建真实需要的目录，不要求所有项目都拥有相同的 `src/`、`tests/` 或 `demo/` 结构。

## 2. 可独立性

每个子项目的 README 应让新读者不依赖根目录文档就能完成以下事情：

1. 理解研究目标与当前状态；
2. 找到上游来源和参考版本；
3. 安装依赖并启动项目；
4. 运行测试或其他验证；
5. 区分上游内容、本地重写与原创扩展；
6. 找到源码仓库、研究记录和在线演示。

不要通过 `../another-project` 引用兄弟项目源码。确需共享时，应使用正式包、独立共享仓库，或在形成重复需求后再设计根级工作区。

## 3. 研究可复现性

- 锁定并记录上游 tag 或 commit，不只记录默认分支名。
- 记录获取日期、运行环境、依赖版本和准确命令。
- 先保存上游基线结果，再做修改；失败也要记录错误和环境。
- 结论必须能追溯到命令输出、测试、截图、基准数据或代码位置。
- 不提交密钥、个人数据、依赖缓存和可再生成的大型构建产物。

## 4. 许可证与来源

- 复制任何第三方代码或素材前，先确认它允许当前用途。
- 按上游要求保留 LICENSE、NOTICE、版权头和署名。
- 代码许可证不一定覆盖字体、图片、音频、模型或数据集，需要分别检查。
- 根仓库许可证只覆盖明确声明的原创内容，不能替代第三方许可。

## 5. 根索引维护

创建、重命名、拆仓、部署或归档子项目时，同一变更中更新根 `README.md`。索引至少保持以下信息准确：研究主题、技术栈、状态、本地路径、上游、独立仓库、演示地址和许可证。

## 6. 将来拆分为独立仓库

子项目成熟后，可以使用保留路径历史的方式拆分。拆分后：

- 总仓库保留研究摘要和链接；
- 独立仓库拥有自己的 README、LICENSE、Issues、CI 和发布配置；
- 只有总仓库构建确实需要锁定该仓库源码时，才把它作为 submodule；
- 普通关联只使用链接，避免增加克隆和维护复杂度。
